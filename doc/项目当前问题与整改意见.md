# 物联网设备事件识别项目当前问题与整改意见

## 1 总体判断

项目已经完成了实验环境搭建、部分真实流量采集、HA 日志导出、时间窗对齐、基础特征提取和简易模型训练，证明了完整链路能够运行。但当前成果仍属于小规模概念验证，尚不足以支持“PU-MIL-自动编码器方法已经有效”或“模型达到稳定识别性能”的结论。

当前最关键的问题不是模型容量不足，而是实验任务定义、数据规模、数据可追溯性、PU 学习实现和评估方法尚未闭合。整改顺序应为：先重建自动化数据采集和 P/U 数据管线，再建立无泄漏的会话级评估，最后完成与设计一致的 PU-MIL-自动编码器模型。

## 2 当前已有成果

可以从当前工作区确认的成果包括：

- 已建立包含路由器、镜像抓包、IoT 设备、HA 主机和抓包主机的实验环境；
- 已获得 Yeelight 灯泡和小米摄像头等设备的原始流量、清洗流量和 HA 日志；
- 已观察到若干稳定的包长与方向序列；
- 已实现日志时间解析、目标设备流量过滤和时间窗划分；
- 已实现 7 维数据包特征提取和标准化；
- 已实现自动编码器、实例分类器和包级池化的原型；
- 已保存一个模型权重和一组标准化参数；
- 已形成申报书和中期报告，对项目目标和技术路线进行了整理。

这些成果为整改提供了可复用基础，但现有实验结论需要在新数据和新评估流程下重新验证。

上述拓扑描述是既有采集环境的历史记录。后续若按 [热点替代方案](厂商App异网自动化实验设计.md#32-场地受限时抓包主机兼作实验热点) 采集，应把新拓扑作为独立会话条件记录，并验证 AP 接口抓包覆盖率、重新校准时间窗及评估跨拓扑泛化；旧镜像会话与热点会话不能默认视为同分布。

## 3 问题清单与整改意见

### 3.1 任务定义与实际代码不一致

**现状**

项目目标是识别具体设备事件，但当前日志解析仅提取时间戳，没有把日志中的状态或事件类型写入标签。所有状态变化都被合并成同一正类。现有配置一次只处理一个设备 IP和一份日志。

**影响**

- 当前模型更接近“目标时间附近是否发生过任意活动”的检测器；
- 无法证明能够区分开、关、模式切换、移动追踪等具体事件；
- 不同事件的实验数据容易被错误混合。

**整改意见**

1. 建立明确的事件字典，定义设备、事件类型、前置状态、目标状态和可接受确认条件。
2. 日志解析输出 `device_id`、`event_type`、`state_before`、`state_after` 和时间戳，而不是只输出时间。
3. 每个事件拥有独立的 P/U 数据集，或采用明确设计的多类扩展方法。
4. 对无法从当前可观测流量中区分的事件合并标签，不强行使用复杂模型区分。

**验收标准**

任意训练样本都能追溯到确定的设备、事件定义、会话和原始 PCAP 时间区间。

### 3.2 数据采集依赖人工操作

**现状**

事件依赖人工操作厂商 App，重复次数有限，点击时间缺少统一记录，操作失败和状态确认也没有结构化保存。

**影响**

- 正包规模不足；
- 事件间隔和顺序带有人为规律；
- 难以复现实验；
- 无法准确测量 App 操作、网络流量和 HA 日志之间的延迟。

**整改意见**

采用实体 Android 手机、Appium 和 UiAutomator2 自动操作厂商 App。手机使用与实验网隔离的公共 Wi-Fi或蜂窝网络，HA 仅被动记录。自动化程序应记录点击前后时间、App 确认、HA 状态、失败原因和事件 ID。

**验收标准**

单设备两类事件各自动执行 20 次，操作成功率和状态确认率均达到 95%，每次事件都有完整元数据。

### 3.3 当前工作区的数据规模和报告不完全一致

**现状**

中期报告提到 4 款设备、10 种事件和 25 万余数据包，但当前工作区能直接核查的原始抓包约为 9.6 万个数据包，主要涉及灯泡和摄像头。三个摄像头预处理文件内容完全相同，说明存在重复文件或命名错误。

**影响**

- 无法从仓库复现报告中的数据规模；
- 重复文件可能被误当作独立样本；
- 数据来源、处理版本和模型权重之间缺少对应关系。

**整改意见**

1. 找回报告所述但未进入工作区的数据。
2. 为每个原始 PCAP、日志和派生文件计算哈希。
3. 建立会话清单，记录设备、事件、采集时间、App 版本、固件、网络类型和文件哈希。
4. 删除或隔离重复派生文件，并保留原因说明。
5. 任何报告数字必须由可执行统计脚本生成。

**验收标准**

报告中的设备数、事件数、会话数、事件次数和数据包数量均能由数据清单自动统计得到。

### 3.4 时间窗和日志延迟没有经过校准

**现状**

当前配置使用固定日志延迟和固定 10 秒窗口；中期报告则描述了不同的 5 秒窗口。现有 Yeelight 日志有部分事件早于抓包开始时间，导致这些事件没有对应流量。

**影响**

- 正包可能为空或缺失关键流量；
- 未标注集合中混入更多正例；
- 过长窗口混入心跳和其他活动；
- 报告和代码无法相互验证。

**整改意见**

1. 以自动化程序记录的 App 点击区间作为主要时间锚点。
2. 被动记录 App 确认时间和 HA 状态时间。
3. 为每种设备事件先进行至少 30 次延迟试验。
4. 只用试采集或训练会话估计窗口参数，冻结后再评估。
5. 自动拒绝抓包范围之外的事件，并报告缺失数量。

**验收标准**

每种事件都有延迟分布、窗口参数和覆盖率报告，正式数据中不存在静默丢失的事件。

### 3.5 正包和未标注包的构造存在长度偏差

**现状**

当前正包使用事件附近的固定窗口，未标注包则可能由两个事件窗口之间的整个空隙组成。两类包在持续时间和数据包数量上存在明显差异。

**影响**

模型可能只根据包长度、持续时间或数据包数量分类，而不是学习事件流量模式。

**整改意见**

1. 正包和未标注包使用相同的固定窗口机制。
2. 未标注包从连续流量中滑窗产生，不把整个事件间隙视为一个包。
3. 对包时长、实例数和空闲间隔进行分布检查。
4. 增加只使用包长度或实例数的捷径基线；若捷径基线表现很高，应暂停模型实验并修正数据。

**验收标准**

P 与 U 的窗口长度规则一致，模型输入中不存在由数据构造方式直接暴露标签的字段。

### 3.6 当前损失函数不符合 PU 学习设定

**现状**

当前 `pu_loss` 对正包使用正类对数损失，对未标注包使用乘以 0.1 的负类损失。本质上仍把全部未标注包当成低权重负类。

**影响**

- 未标注集合中的真实正例被作为负类惩罚；
- 正例污染越高，训练偏差越严重；
- 不能据此声称实现了 nnPU、PULDA 或严格的 PU 风险。

**整改意见**

1. 明确选择并完整实现一种 PU-MIL-AE 算法，而不是继续使用加权负类近似。
2. 训练数据只包含 `P_gold` 和 `U`，不加入人工负包。
3. 显式记录正类先验、标签频率或可靠负例估计方法。
4. 为 PU 损失编写数值测试，检查全正预测、全负预测和混合概率下的风险。
5. 将普通 P/U 当负类方法保留为对照基线，不作为目标模型。

**验收标准**

方法文档、数学公式、代码实现和单元测试一致，未标注标签不会直接进入普通负类交叉熵。

### 3.7 MIL 池化实现与报告不一致

**现状**

报告描述 Noisy-OR 池化，现有 `MILHead` 实际使用实例概率最大值。报告中的代码截图也与当前源文件不完全一致。

**影响**

- 当前代码无法复现报告中的模型；
- 最大值池化只依赖一个实例，可能忽略同一包中的多个相关实例；
- 无法判断结果来自哪一版实现。

**整改意见**

1. 实现数值稳定的 Noisy-OR，并保留 max、mean、attention 作为消融项。
2. 用测试样例验证池化结果和梯度。
3. 模型配置记录池化方法，不允许由代码默认值隐式决定。
4. 报告中的架构图和代码片段从当前版本自动生成或人工核对。

**验收标准**

检查点元数据可以明确指出所用池化函数，重新运行得到相同结构和结果。

### 3.8 自动编码器目标和分类目标缺少实验论证

**现状**

当前模型把实例重构损失与简化分类损失直接相加，没有说明权重、训练阶段或未标注污染条件下的合理性。

**影响**

- 重构目标可能压制事件判别特征；
- 两项损失尺度不同，训练行为难以解释；
- 无法证明自动编码器带来了增益。

**整改意见**

1. 明确采用联合训练还是预训练加微调。
2. 为重构损失和 PU-MIL 损失设置可配置权重。
3. 比较无 AE、冻结 AE、联合 AE三种设置。
4. 记录各损失曲线和编码空间可分性。

**验收标准**

自动编码器的作用由会话级消融实验支持，而不是仅凭训练损失下降判断。

### 3.9 数据标准化存在泄漏

**现状**

当前流程先对全部包拟合 StandardScaler，再划分训练、验证和测试集。

**影响**

测试集统计信息进入训练流程，评估结果偏乐观。

**整改意见**

先按会话划分数据，只在训练会话上拟合标准化器，再用于验证、测试和审计集。标准化器与模型检查点一起保存，并记录特征版本。

**验收标准**

训练日志明确列出标准化器使用的会话 ID，测试会话不在其中。

### 3.10 当前交叉验证不是真正的五折验证

**现状**

代码执行五次不同随机种子的 8:1:1 留出，同一样本可能在不同轮次重复出现在训练或测试集中。划分没有分层，也没有按会话分组。部分验证集可能只有一个类别，单轮测试样本非常少。

**影响**

- 各轮结果高度相关；
- 同一次连续抓包的相邻窗口发生泄漏；
- F1和准确率受类别比例强烈影响；
- 平均指标不能代表跨会话泛化。

**整改意见**

1. 按 `session_id` 使用 Group K-fold 或留一会话验证。
2. 保证验证集和审计集具有评价所需的真值组成。
3. 报告每个会话结果、均值、标准差和置信区间。
4. 最终审计集在所有模型和阈值确定后只使用一次。

**验收标准**

任意原始数据包只属于一个数据集分区，训练和测试来自不同独立会话。

### 3.11 模型保存与评估对象不一致

**现状**

训练过程会保存验证损失最优的权重，但函数最后返回的是最后一轮模型，后续评估没有重新加载最优检查点。

**影响**

报告指标、保存的权重和实际评估模型可能不是同一个模型。

**整改意见**

训练完成后必须重新加载最优验证检查点，再执行验证和测试。检查点同时保存模型配置、特征版本、标准化器哈希、数据划分和随机种子。

**验收标准**

评估报告中的检查点哈希与交付模型文件一致。

### 3.12 阈值配置和指标解释不一致

**现状**

全局配置阈值为 0.5，评估函数默认阈值为 0.4。阈值没有在验证集上选择，也没有解释依据。

**影响**

不同运行可能使用不同阈值，F1和召回率不可比较。

**整改意见**

阈值只能根据验证会话和预先定义的目标选择，例如最大化验证 PR-F1 或满足误报率上限。测试和最终审计时冻结阈值。

**验收标准**

每份评估报告记录阈值、选择规则和对应验证会话。

### 3.13 当前模型权重缺少可复现来源

**现状**

保存的标准化参数与当前代码重新计算的部分统计量不一致，模型文件也没有训练配置、数据版本或指标记录。使用当前权重对现有 63 个包进行核查时，多个常用阈值下会把全部样本预测为正类，整体 AUROC接近随机水平。

**影响**

- 无法确认模型来自哪一版数据和代码；
- 当前权重不能作为后续性能基线；
- 较高 F1可能只是正类占比较高造成的表象。

**整改意见**

1. 将现有权重标记为历史原型，不再作为正式结果。
2. 完成新数据和新训练流程后从头训练。
3. 每次实验生成唯一运行 ID和机器可读指标文件。
4. 模型、标准化器、配置、数据清单和 Git 提交哈希一起归档。

**验收标准**

给定运行 ID，可以从指定 Git 提交和数据清单重新得到相近结果。

### 3.14 特征表达不足且存在不可辨识事件

**现状**

当前仅使用包长、方向、包间隔、协议、TTL、TCP 窗口和 payload 长度。已有灯泡数据表明某些开关事件的包长方向序列没有区别。

**影响**

如果两个事件在当前抓包位置的可观测分布相同，模型无论多复杂都无法稳定区分。

**整改意见**

1. 扩充带方向包长序列、TLS record 长度、突发包数量、上下行字节、请求响应间隔、流持续时间和包长 n-gram。
2. 研究设备到云、设备到路由器等多流的联合时间模式。
3. 先用简单序列匹配和树模型执行可辨识性测试。
4. 若独立会话中仍接近随机水平，合并标签或调整观测点，不继续堆叠深度模型。
5. 记录可能导致跨环境失效的 IP、端口和云端地址特征，避免模型只记住固定端点。

**验收标准**

每对事件在独立会话上都有可辨识性报告；无法区分的标签有明确合并或降级决定。

### 3.15 代码可移植性和工程质量不足

**现状**

路径写死为本地 `D:` 盘；缺少依赖清单、项目说明、数据清单、单元测试和统一命令入口；异常被广泛捕获，警告被全局关闭；部分输出文件扩展名与实际写入格式可能不一致。

**影响**

项目换电脑后无法直接运行，错误容易被隐藏，后续成员难以接手。

**整改意见**

1. 使用 YAML 配置和相对路径。
2. 增加 README、环境依赖和统一命令入口。
3. 以结构化日志替代大量控制台输出。
4. 不再全局关闭警告，异常必须包含文件和会话信息。
5. 为日志解析、窗口生成、P/U 构造、池化、损失和会话划分编写单元测试。
6. 明确 PCAP 与 PCAPNG 的读写格式。

**验收标准**

在一台新电脑上按照 README 可以完成环境检查、数据构建、训练和评估。

### 3.16 报告结论超过当前证据

**现状**

中期报告给出准确率和 F1，并声称完成多设备、多事件数据集和若干模型模块，但当前工作区缺少完整划分、逐样本预测、混淆矩阵、运行日志和相应代码版本。

**影响**

结论难以复核，也会使后续实验错误地把未经验证的数字当作基线。

**整改意见**

1. 将现有指标明确标记为早期原型结果。
2. 新报告只引用自动生成的实验表格。
3. 每项结果同时给出数据版本、会话划分、模型版本、阈值和样本量。
4. 明确区分训练结果、验证结果和独立审计结果。

**验收标准**

报告中的每个数字均可定位到运行 ID、指标文件和检查点。

### 3.17 原型系统和轻量化工作启动过早

**现状**

计划包含模型剪枝、蒸馏、边缘部署和完整系统界面，但当前模型仅有约 6800 个参数，主要问题仍是数据和评估可信度。

**影响**

过早投入部署和界面会分散资源，无法解决研究结论不可靠的问题。

**整改意见**

在完成自动化采集、会话级评估和有效模型基线之前，暂停剪枝、蒸馏、分布式训练、贝叶斯调参和复杂界面开发。短期原型只需实现从 PCAP 到事件时间线的离线命令行流程。

**验收标准**

只有在目标模型稳定优于简单基线且跨会话有效后，才进入部署优化阶段。

## 4 整改优先级

| 优先级 | 整改内容 | 主要产出 |
|---|---|---|
| P0 | 厂商 App 异网自动化、事件日志、连续抓包 | 可重复批量采集流程 |
| P0 | 数据清单、时间同步、P/U 构造 | 可追溯的 P/U 数据集 |
| P0 | 会话级数据划分和无泄漏标准化 | 可信训练、验证和审计分区 |
| P1 | 与设计一致的 PU 损失、MIL 池化和 AE 训练 | 可验证目标模型 |
| P1 | 简单规则、树模型和无 AE 基线 | 判断深度模型是否真正有增益 |
| P1 | 独立评价审计集 | 可信误报率、F1和 PR-AUC |
| P2 | 多设备和多 App 适配器 | 扩展数据覆盖 |
| P2 | 离线事件时间线原型 | 项目展示和集成验证 |
| 暂缓 | 剪枝、蒸馏、分布式训练、复杂前端 | 等模型有效后再启动 |

## 5 建议的近期整改周期

### 第一周 自动化采集闭环

- 完成一款厂商 App 的 Appium 适配器；
- 完成事件 JSONL、连续抓包和 HA 被动日志导入；
- 完成公共 Wi-Fi或蜂窝网络隔离预检；
- 两类事件各试采集 20 次；
- 修正时间窗口和失败处理。

### 第二周 数据与评估闭环

- 完成 5 个独立会话；
- 每类事件获得约 200 个确认正包；
- 生成固定窗口未标注包；
- 完成会话级训练、验证和审计划分；
- 建立包长方向签名和简单机器学习基线。

### 第三周 模型闭环

- 实现目标 PU-MIL-自动编码器；
- 完成 max、Noisy-OR、无 AE和普通 P/U 当负类的消融；
- 重新训练并加载最佳检查点；
- 在独立审计集上一次性评价。

### 第四周 结果整理

- 生成可复现实验表格和图；
- 修订中期报告中过度结论；
- 完成从 PCAP 到事件时间线的离线演示；
- 决定是否扩展到更多设备和事件。

## 6 整改完成的总体判据

项目只有同时满足以下条件，才能视为从概念验证进入可信实验阶段：

1. 事件由厂商 App 自动触发，手机不属于实验网络；
2. HA 只作为被动日志源；
3. 训练数据只有已确认正包和未标注包；
4. 数据按独立会话划分且标准化无泄漏；
5. 模型代码与 PU-MIL-AE 方法说明一致；
6. 最佳检查点、配置、数据清单和 Git 提交可以共同复现结果；
7. 最终指标来自完全独立、未参与模型选择的评估审计集；
8. 目标模型在跨会话结果上稳定优于简单基线。
