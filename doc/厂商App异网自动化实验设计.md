# 厂商 App 异网自动化事件采集实验设计

## 1 设计目标

本方案用于自动生成家庭物联网设备事件流量数据。事件必须由设备厂商 App 发起，Home Assistant 只作为被动状态日志源，不得通过 Home Assistant 服务、脚本或自动化触发设备事件。

方案需要同时满足以下目标：

1. 厂商 App 所在手机不接入实验网络，可使用实验室公共 Wi-Fi。
2. 自动化操作尽可能复现真实用户在厂商 App 中的点击流程。
3. 每次操作均产生可追踪的事件编号、操作时间、确认结果和对应流量区间。
4. 抓包、App 操作记录与 Home Assistant 被动日志能够在同一时间轴上对齐。
5. 支持数百次重复实验，并能识别、保留和排除失败操作。
6. 数据按独立采集会话划分，避免同一次连续抓包同时进入训练集和测试集。

## 2 是否需要 Android Root

### 2.1 结论

正常的厂商 App 界面自动化不需要 Root。

推荐使用真实 Android 手机、Appium 和 UiAutomator2。手机只需要：

- 开启开发者选项；
- 开启 USB 调试；
- 首次连接时授权实验控制主机；
- 允许 Appium 安装并运行自动化辅助组件；
- 保持屏幕解锁，关闭可能中断自动化的省电和后台限制。

Appium 官方 UiAutomator2 驱动要求真实设备开启 USB 调试并能被 `adb devices -l` 识别为 `online`，没有要求设备获得 Root 权限。Android 官方文档同样将 USB 调试作为开发工具与设备通信的标准方式。

### 2.2 本项目不应使用 Root 的原因

Root 不但没有必要，还可能降低实验真实性：

- Root、注入框架或修改系统证书可能被厂商 App 检测；
- Root 可能改变 App 的安全策略、网络行为和后台运行方式；
- Root 后的系统状态难以代表普通家庭用户设备；
- 不同手机的 Root 环境难以复现。

本项目不需要读取厂商 App 私有数据库、不需要在手机端抓包、不需要解密 TLS，也不需要直接调用 App 内部函数，因此没有引入 Root 的必要。

### 2.3 不需要 Root 但可能遇到的限制

以下情况可能使界面自动化变得困难，但仍不意味着必须 Root：

- App 使用自绘控件，UiAutomator 无法获得控件 ID 或文字；
- App 使用安全窗口，禁止截图或隐藏页面结构；
- 登录过程包含验证码、生物识别或滑块验证；
- 厂商 App 更新后页面结构和控件 ID 发生变化；
- 手机厂商的省电机制终止 Appium 辅助进程；
- 弹窗、升级提示或网络异常覆盖目标按钮。

建议的降级顺序是：

1. 使用控件资源 ID、文字或无障碍描述定位；
2. 使用页面层级和相对位置定位；
3. 固定手机分辨率和显示缩放后使用坐标点击；
4. 使用截图模板识别按钮位置；
5. 对无法可靠自动化的少数场景使用机械点击装置。

Root 不应被列为常规降级方案。

## 3 推荐实验架构

### 3.1 推荐部署方式

手机可以在物理上位于实验室内，但在网络上必须位于实验网络之外。推荐结构如下：

```text
                  公共 Wi-Fi、4G 或 5G
真实 Android 手机  ───────────────────>  厂商云
       │                                    │
       │ USB ADB                            │ 云端设备指令
       │                                    ▼
实验控制与抓包主机                    实验网络中的 IoT 设备
       │                                    │
       │ 本地记录                           │
       ├── actions.jsonl                    ├── 设备与路由器流量
       ├── appium.log                       └── 设备与云端流量
       └── traffic.pcapng                         │
                                                  ▼
                                        Home Assistant 被动日志
```

Appium 控制数据通过 USB 传输，不经过实验网络。手机可以连接实验室公共 Wi-Fi，也可以使用蜂窝网络；关键约束是手机不能连接实验路由器或与 IoT 设备、HA 主机处于同一二层网络或可直接互通的实验网段。

公共 Wi-Fi 应作为一种正式触发网络类型单独记录。公共 Wi-Fi 与蜂窝网络可能具有不同的出口地址、DNS、时延和连接保持行为，两类会话不应在没有标记的情况下混合。

### 3.2 场地受限时：抓包主机兼作实验热点

可用“抓包主机的独立上行网络接口接外网 + 支持 AP 模式的无线接口开实验热点”替代实验路由器和镜像口。IoT 设备接入该热点；实验手机仍通过 USB 接受 Appium 控制，并使用**与实验热点隔离**的公共 Wi-Fi 或蜂窝网络访问厂商云。

```text
Android 实验手机 ──公共 Wi-Fi/蜂窝网络── 厂商云
       │                                  │
       │ USB ADB                          │ 云端指令
       ▼                                  ▼
抓包与热点主机 ── 外网上行（建议有线）── 外网
       │ AP 无线接口：设备侧、NAT 前抓包
       └── 实验 SSID ── IoT 设备
                          │
                          └── 可选 HA 被动观测
```

**效果边界：**只要设备实际经热点上网，且在 AP 接口的试抓包中能看到目标设备双向流量，就能保留“异网厂商 App 触发 + 设备侧流量 + 时间对齐”的核心实验目的。它不保证与旧镜像口采集到完全相同的数据：普通 AP 接口通常呈现类似以太网的封装，而非原始 802.11 管理/控制帧；无线重传及部分终端之间的本地流量也不一定可见。网关、DNS、DHCP、NAT、时延和背景流量会变化。旧会话和热点会话须标记不同拓扑，重新校准事件延迟与模型表现，不得直接当作同分布数据合并。

部署与验收按以下顺序执行：

1. 使用两个独立网络角色：稳定的外网上行（优先有线）和支持 AP 模式的无线接口。先检查无线网卡/驱动的 AP 能力及频段；若上行也依赖同一块无线网卡，只有明确支持 STA+AP 并发且现场稳定时才采用，否则增加第二块网卡。
2. 创建仅供 IoT 设备使用的热点，确认其加密为 WPA2/WPA3，设备支持所选 2.4/5 GHz 频段；拒绝开放或 WEP 热点。启用 IP 地址分配、DNS 转发、共享上网/NAT，并为设备保留或记录稳定的热点侧 IP。热点网段不能与上行网或手机网络重叠，且必须纳入手机隔离预检的 `forbidden_cidrs`。不要把实验手机接入此 SSID，也不要打开 USB 网络共享。
3. 在热点 **AP 无线接口**抓包，而不是只抓外网上行接口；后者经过 NAT 后可能只显示主机地址，无法可靠按设备 IP 过滤。常规采集不启用无线 monitor mode，以免干扰热点。先做一次不带过滤器的短时试抓包，核对目标 IP/MAC、双向包、DNS、设备状态变化和 PCAP 时间范围，再确定正式过滤器。若研究目标包含广播发现、ARP 或设备与设备本地通信，先验证这些包确实可见，并调整抓包范围；单纯 `host <设备IP>` 会漏掉非 IP 或不带该 IP 的帧。
4. 如使用 HA 被动日志，确保 HA 仍可访问其观测来源并与抓包主机同步时间，但不得通过 HA 触发设备动作。在另一网络上的手机执行一次厂商 App 操作，确认 App 有回执、设备状态变化、设备侧 PCAP 中有对应流量且 HA 被动日志可对齐。手机到设备 IP 的 `ping` 不通只能作为辅助证据；还要核对手机没有加入实验 SSID、没有通往热点网段的路由，并用实际控制路径排除局域网直连。现有自动预检不替代这些人工拓扑核验。
5. 固定并记录上行类型、AP 网卡与驱动、SSID 标识（不记录密码）、频段/信道、网段、网关、设备 IP/MAC、NAT/DNS 方式、抓包接口、过滤器、固件版本、丢包统计及热点拓扑版本。热点断连、自动重连换 IP 或外网切换后，停止当前正式会话，重新预检并新建会话。

如果试抓包不能稳定覆盖目标设备的双向流量，或者必须研究无线链路层及客户端间流量，就不能宣称与原镜像抓包等效；应恢复可镜像的接入设备或增加独立观测点。NetworkManager 的共享连接会提供 DHCP、DNS 和 NAT；Wireshark 对普通 WLAN 接口与 monitor mode 的可见范围有说明，具体覆盖仍须以现场 PCAP 验证（[NetworkManager 共享模式](https://networkmanager.pages.freedesktop.org/NetworkManager/NetworkManager/nm-settings-nmcli.html)、[Wireshark WLAN 抓包说明](https://wiki.wireshark.org/CaptureSetup/WLAN)）。

### 3.3 手机确实位于远程地点时的扩展方案

如果“异网”还要求手机物理上位于另一地点，则采用两级控制结构：

```text
中央实验编排器
       │ 独立管理网络
       ▼
远程自动化代理主机 ──USB── Android 手机 ──公共 Wi-Fi 或蜂窝网络── 厂商云

实验现场抓包主机 ──镜像口或热点 AP 接口── 实验网络中的 IoT 设备
```

远程代理只负责执行 Appium 操作并写入时间戳。中央编排器负责下发场景编号、收集结果和合并元数据。远程代理、抓包主机和 Home Assistant 主机必须同步时间。

在能够满足网络隔离的情况下，优先采用“手机在实验室内、通过 USB 控制、连接独立公共 Wi-Fi 或蜂窝网络”的方式，因为时间同步和故障处理更简单。

## 4 软件和硬件组成

### 4.1 硬件

- 一台真实 Android 手机，建议 Android 11 或更高版本；
- 稳定的数据 USB 线；
- 运行实验编排程序和 Appium 的控制主机；
- IoT 设备、抓包主机和可选 Home Assistant 主机；接入设备可选原有路由器与镜像交换机，或采用 3.2 节的热点主机方案；
- 可选：远程自动化代理主机或机械点击装置。

### 4.2 软件

- Android SDK Platform Tools；
- Appium；
- Appium UiAutomator2 驱动；
- Python Appium 客户端或其他 WebDriver 客户端；
- `dumpcap`、`tshark` 或现有抓包工具；
- 实验编排程序；
- Home Assistant 被动日志导出程序；
- NTP 时间同步服务。

应在实验元数据中记录 Appium、UiAutomator2、Android、厂商 App 和设备固件的具体版本。

## 5 自动化程序分层设计

### 5.1 通用实验编排层

通用层不包含厂商 App 的页面细节，只负责：

- 读取实验计划；
- 创建会话和事件编号；
- 启动和停止抓包；
- 调用指定 App 适配器；
- 记录操作前后时间；
- 随机化事件顺序与等待时间；
- 接收操作结果；
- 保存日志和会话元数据；
- 发生异常时安全停止实验。

### 5.2 厂商 App 适配器层

每个厂商 App 实现统一接口：

```text
launch_app()
ensure_logged_in()
open_device(device_id)
read_state()
perform_event(event_type)
wait_for_app_acknowledgement()
verify_app_state(expected_state)
recover_to_known_page()
close_app()
```

页面控件定位顺序为：

1. `resource-id`；
2. `content-description`；
3. 可见文字；
4. 页面层级中的相对关系；
5. 固定坐标或图像模板。

不建议把坐标写在通用层中。坐标、控件 ID 和页面跳转路径都应封装在对应 App 适配器内。

### 5.3 设备状态机

每个设备必须定义合法状态和事件。例如灯泡：

```text
OFF --turn_on--> ON
ON  --turn_off-> OFF
ON  --set_color-> ON
ON  --set_brightness-> ON
```

执行事件前先检查当前状态。状态不满足时，不得静默执行额外复位操作；复位操作本身也会产生流量，必须作为独立事件记录，或者在正式会话开始前完成。

## 6 单次事件执行流程

每次自动化事件按照以下顺序执行：

1. 确认 App 已登录并处于目标设备页面。
2. 读取 App 当前显示的设备状态。
3. 检查该状态是否满足事件前置条件。
4. 随机等待一段空闲时间。
5. 生成唯一 `event_id`。
6. 记录点击命令发出前的主机时间 `t_cmd_before`。
7. 通过 Appium 点击事件控件。
8. 记录 Appium 点击命令返回后的主机时间 `t_cmd_after`。
9. 等待 App 成功提示或状态变化，记录 `t_app_ack`。
10. 将 App 显示状态与预期状态比较。
11. Home Assistant 在后台被动记录设备状态变化，后处理时得到 `t_ha_state`。
12. 根据 App 与 HA 的结果确定本次事件状态。
13. 进入冷却时间，再执行下一个事件。

真实点击发生在 `[t_cmd_before, t_cmd_after]` 区间内。该区间宽度应作为时间标注不确定性保存，而不是假定点击恰好发生在其中某一端。

## 7 事件结果分类

每次操作必须归入以下状态之一：

| 状态 | 含义 | 是否进入金标准正包 |
|---|---|---|
| `confirmed` | App 操作成功，且 HA 被动日志或其他观测确认状态变化 | 是 |
| `app_ack_only` | App 显示成功，但 HA 未记录或目标状态无法独立确认 | 否，先进入待复核集合 |
| `ha_only` | HA 出现状态变化，但 App 未显示成功 | 否，需检查并发事件 |
| `failed` | App 明确显示操作失败 | 否 |
| `timeout` | 在规定时间内没有结果 | 否 |
| `unexpected_state` | 最终状态与实验计划不一致 | 否 |
| `automation_error` | 页面跳转、控件定位或 Appium 会话失败 | 否 |

失败后重新操作必须创建新的 `event_id`，不得覆盖失败记录。失败产生的网络流量应保留，用于诊断，但不能与成功事件混为一类。

## 8 时间同步与事件对齐

### 8.1 时钟要求

- 抓包主机、Home Assistant 主机和远程代理主机使用同一 NTP 时间源；
- 所有持久化时间使用 UTC Unix 时间戳，并尽可能保留微秒或纳秒；
- 会话开始与结束时记录各主机时钟偏移；
- 同一台主机内部的等待和超时判断使用单调时钟；
- 手机系统时间不作为主要对齐依据。

推荐目标是主机间偏差小于 100 毫秒；无法达到时，应至少将偏差控制在 500 毫秒以内并记录实际偏差。

### 8.2 时间窗口确定

不应继续使用统一的固定日志偏移量。先为每个设备事件执行至少 30 次试采集，统计：

- `t_cmd_before` 到首个相关流量突发的延迟；
- 流量突发持续时间；
- `t_cmd_before` 到 `t_app_ack` 的延迟；
- `t_cmd_before` 到 `t_ha_state` 的延迟；
- 不同会话之间的延迟波动。

根据试采集数据为每种事件确定窗口前移量、后移量和保护区。窗口参数只能使用试采集集或训练集估计，确定后冻结，不能根据测试集结果反复调整。

## 9 数据标签体系

训练数据只由正包和未标注包组成，不引入已标注负包。另设失败数据和评估审计数据，但评估审计数据绝不参与训练或模型选择。

### 9.1 金标准正包 `P_gold`

满足以下条件：

- App 自动化操作状态为 `confirmed`；
- 事件前置状态正确；
- 流量抓取完整；
- 时间同步检查通过；
- 窗口内没有其他人工或自动化事件。

正包只需要保证包含目标事件相关流量，不要求包内每个数据包都属于目标事件。

### 9.2 未标注包 `U`

来自长时间连续流量。除已确认正包窗口和失败操作保护区外，其余固定长度窗口均作为未标注包。未标注包中允许存在遗漏的目标事件，也允许包含非目标活动。该集合用于 PU 学习，不得在普通二分类损失中直接全部作为负类。

空闲时段不能作为训练用负包。即使实验计划中没有主动触发目标事件，也应将这些窗口视为未标注包，因为设备可能存在自动状态变化、云端行为或日志遗漏。

### 9.3 评估审计集 `E_eval`

PU-MIL-AE 训练不使用负包，但研究仍需判断模型是否把非目标流量误报为目标事件。因此另建仅用于最终评价的审计集：

- 由人工复核或受控实验确认窗口内目标事件是否出现；
- 包含目标事件存在和目标事件缺席两种真值；
- 不进入训练、标准化器拟合、阈值选择或超参数搜索；
- 与训练、验证数据来自不同采集会话；
- 只用于计算精确率、召回率、F1、误报率和每小时误报次数。

审计集中“目标事件缺席”的窗口是评价真值，不是 PU-MIL-AE 的训练负包。若完全不构建此类评价真值，只能报告正包召回或 PU 风险代理量，无法可信计算误报率、精确率和 F1。

### 9.4 失败与待复核数据

包括 App 操作失败、App 与 HA 状态冲突、时间异常和抓包异常。单独存放，不进入主要训练和测试。

## 10 实验计划格式

建议使用 YAML 描述实验计划：

```yaml
experiment_id: camera_remote_app_v1
phone:
  phone_id: android_phone_01
  network: public_wifi
  experiment_network_forbidden: true
app:
  vendor: example_vendor
  package: com.example.vendor
  version: 1.2.3
device:
  device_id: camera_01
  firmware: 4.5.6
sessions:
  count: 5
  repetitions_per_event: 40
  idle_range_seconds: [10, 30]
  cooldown_seconds: 10
events:
  - event_type: motion_tracking_on
    required_state: motion_tracking_off
    expected_state: motion_tracking_on
  - event_type: motion_tracking_off
    required_state: motion_tracking_on
    expected_state: motion_tracking_off
```

正式执行时应根据状态机生成合法且随机化的事件序列，而不是直接把事件列表完全随机打乱。

## 11 事件记录格式

## 13 推荐采集规模

### 13.1 试采集阶段

- 选择 1 台设备和 2 个状态互逆的事件；
- 每类事件执行 20 次；
- 验证 Appium 稳定性、时间对齐、网络隔离和正包窗口；
- 人工检查全部 40 次操作。

### 13.2 正式采集阶段

- 每种事件采集 5 个独立会话；
- 每个会话每种事件执行 40 次；
- 每种事件目标获得 200 个确认正包；
- 每个会话保留完整连续流量，并按固定窗口构造未标注包；
- 另从完全独立的会话中构建评估审计集，但不将其中的目标缺席窗口加入训练。

独立会话尽量分布在不同时间段和不同日期。部分会话应重新启动手机 App、IoT 设备或网络连接，以覆盖长连接和缓存状态变化。

如果有 3 种事件，正式阶段约产生 600 个事件包。按平均 20 秒空闲间隔估算，纯等待时间约 3.3 小时，考虑状态确认和恢复后可分一至两天完成。

## 14 事件顺序与随机化

为了避免模型学习人工实验节奏，应做到：

- 空闲时间从指定范围内随机采样；
- 合法事件顺序在状态机约束下随机化；
- 不同会话采用不同随机种子；
- 不使用完全固定的开关交替周期；
- 适量加入实验网络背景流量；
- 记录 App 重启、设备重连和异常恢复行为。

随机种子必须写入 `session.yaml`，以便复现实验计划。

## 15 抓包策略

- 每个会话只启动一次连续抓包，避免逐事件启停带来的时间和文件管理误差；
- 文件名使用 `session_id`，不要直接使用事件类型命名；
- 抓包过滤器只用于限制目标设备范围，不应提前过滤特定包长或协议；
- 保留原始 PCAPNG，所有清洗和窗口切分均生成派生文件；
- 原始抓包只读保存，不在其上直接覆盖；
- 同时记录接口、过滤器、抓包工具版本和丢包统计；
- 热点方案记录 AP 接口和 NAT 前设备 IP，并先用短时试抓包确认双向覆盖；
- 会话开始前和结束后保留一段空闲背景流量。

## 16 数据集划分与评估

正包和未标注包必须按 `session_id` 划分：

- 训练集：3 个会话；
- 验证集：1 个会话；
- 测试集：1 个完全独立会话。

不得把同一会话内的事件窗口随机拆分到不同集合。特征标准化器只在训练会话上拟合，决策阈值只在验证会话上选择。最终评估审计集使用额外独立会话，不参与任何训练决策。

训练阶段只能输入 `P_gold` 和 `U`。任何从 `U` 中推断出的可靠负例、负类风险或类别先验，必须由 PU 算法内部估计并记录，不能被写回为人工负标签。

建议报告：

- 每类事件的精确率、召回率和 F1；
- PR-AUC 和 ROC-AUC；
- 每小时误报次数；
- 不同会话的均值与标准差；
- 自动化成功率和标签确认率；
- App 点击到流量、App 确认和 HA 日志的延迟分布。

## 17 质量控制与验收条件

### 17.1 每次会话前

- 手机已连接指定公共 Wi-Fi 或蜂窝网络，且无法接入实验网段；
- USB 网络共享关闭；
- `adb devices -l` 中手机状态为 `online`；
- 厂商 App 已登录；
- App 自动更新关闭；
- 抓包接口和磁盘空间正常；热点方案还须确认 AP 接口有双向设备流量；
- IoT 设备、当前网关（路由器或热点主机）和已启用的 HA 状态正常；
- 所有主机时钟同步；
- 手机未出现在实验网络设备列表中。

### 17.2 每次会话后

- PCAP 覆盖完整会话时间；
- 事件记录条数与计划一致；
- 每个 `event_id` 唯一；
- HA 日志和动作日志时间范围重叠；
- Appium 日志无未处理异常；
- 抓包丢包率在允许范围内；
- 正包窗口不重叠，或重叠事件被明确标记；
- 失败、超时和重试没有被覆盖。

### 17.3 建议验收指标

- Appium 点击流程成功率不低于 95%；
- 成功操作中状态确认率不低于 95%；
- 每类事件最终保留不少于 180 个确认正包；
- 测试会话未参与窗口参数、标准化参数或阈值选择；
- 实验手机在全部正式会话中均未加入实验网络；
- 从事件记录可以追溯到唯一会话、PCAP 时间区间和 HA 被动日志记录。

## 18 风险和应对措施

| 风险 | 影响 | 应对措施 |
|---|---|---|
| 厂商 App 更新 | 控件 ID 或页面路径改变 | 关闭自动更新，记录版本，使用独立适配器 |
| App 使用自绘控件 | 无法通过控件定位 | 相对位置、固定坐标、图像识别或机械点击 |
| 验证码或登录过期 | 批量实验中断 | 会话前检查登录状态，验证码只允许人工完成 |
| 公共 Wi-Fi 或蜂窝网络波动 | 云端响应延迟增加 | 保存网络类型、延迟和失败记录，不静默重试 |
| 云端限频 | 操作失败或设备离线 | 增加随机间隔，限制连续运行时长 |
| 手机省电杀进程 | Appium 会话中断 | 关闭电池优化，保持充电和亮屏 |
| 设备最终状态未知 | 错误正标签 | 仅将双重确认事件纳入 `P_gold` |
| 固定操作节奏 | 模型学习周期伪特征 | 随机等待和分会话采集 |
| HA 日志延迟变化 | 时间窗偏移 | 以 App 点击为主锚点，按事件估计延迟分布 |
| 远程主机时钟漂移 | 标签与流量错位 | NTP 同步并保存时钟偏移 |

## 19 新实验设计需要程序完成的任务

### 19.1 实验配置与清单管理

程序需要读取统一的 YAML 配置，完成以下工作：

- 定义实验、会话、手机、App、设备、事件和网络类型；
- 校验事件前置状态和状态转换是否合法；
- 生成 `experiment_id`、`session_id` 和 `event_id`；
- 保存随机种子、软件版本、App 版本和设备固件；
- 检查必填字段，拒绝缺少设备 IP、事件类型或会话信息的实验。

### 19.2 Android 与厂商 App 自动化

- 检查手机是否通过 USB ADB 在线；
- 启动 Appium 会话并恢复到已知页面；
- 调用不同厂商 App 适配器；
- 读取 App 当前状态并执行目标事件；
- 记录点击前、点击后和 App 确认时间；
- 对弹窗、页面丢失、登录过期和超时进行分类处理；
- 失败重试时创建新事件记录，不覆盖原记录；
- 保存必要截图和 Appium 日志。

### 19.3 连续抓包管理

- 会话级启动和停止抓包；
- 记录抓包接口、过滤器、工具版本和丢包统计；
- 保证 PCAP 覆盖会话前后保护时间；
- 原始 PCAP 只读保存；
- 异常退出时尽量关闭抓包并保存会话状态。

### 19.4 HA 被动日志导入

- 导入或接收 HA 状态日志，但不调用任何设备控制服务；
- 标准化时间戳、实体 ID、状态和属性；
- 将 HA 状态变化与 `event_id` 进行后处理关联；
- 标记 App 与 HA 结果一致、缺失或冲突的情况。

### 19.5 时间同步与对齐

- 保存各主机的时钟偏移检查结果；
- 以 App 点击区间作为主要时间锚点；
- 统计每类事件的 App 确认延迟和 HA 日志延迟；
- 仅使用试采集或训练会话估计窗口参数；
- 检查事件窗口重叠并生成告警。

### 19.6 P 与 U 数据生成

- 从 `confirmed` 事件生成 `P_gold`；
- 从连续流量生成固定长度的 `U`；
- 从 `U` 中排除已确认正包和失败操作保护区，但不将剩余窗口标为负类；
- 保存每个包的来源会话、起止时间、事件 ID和数据包数量；
- 防止相同数据包跨训练、验证和测试会话重复出现。

### 19.7 特征与标准化

- 提取单包、突发、流、序列和上下文特征；
- 保留特征版本和字段定义；
- 标准化器只在训练会话上拟合；
- 对不同长度的包执行掩码或长度无关的聚合；
- 检查包时长、包数量等潜在标签捷径。

### 19.8 PU-MIL-自动编码器模型

- 自动编码器完成实例级编码与重构；
- MIL 层实现与设计一致的 Noisy-OR 或其他明确指定的可微池化；
- PU 目标函数不得把全部 `U` 当作负类；
- 显式记录类别先验、标签频率或可靠负例估计方法；
- 支持模型各组件的消融实验；
- 保存最佳验证检查点并在评估前重新加载；
- 保存每次运行的种子、配置、损失曲线和模型摘要。

### 19.9 会话级划分与评估

- 按 `session_id` 划分训练、验证和测试数据；
- 支持 Group K-fold 或留一会话评估；
- 验证阶段只使用 P/U 设定允许的信息选择阈值和超参数；
- 最终一次性读取独立 `E_eval` 计算分类指标；
- 输出混淆矩阵、PR-AUC、ROC-AUC、每小时误报次数和会话间波动；
- 明确区分训练指标、验证指标和最终审计指标。

### 19.10 数据质量与可追溯性

- 自动执行会话前后质量检查；
- 校验事件数量、唯一 ID、时间覆盖和文件哈希；
- 生成从模型样本到原始 PCAP 和事件记录的可追溯索引；
- 不在日志和仓库中保存访问令牌、账号密码或公共 Wi-Fi 密码；
- 生成机器可读的会话质量报告。

### 19.11 推荐实现优先级

| 优先级 | 程序任务 | 完成标志 |
|---|---|---|
| P0 | 配置、Appium 适配器、事件日志、连续抓包 | 单设备可稳定完成 20 次自动事件并生成完整记录 |
| P0 | 网络隔离预检、时间同步、HA 日志导入 | 每个事件可追溯到 App 操作、HA 日志和 PCAP 区间 |
| P1 | P/U 生成、会话级划分、训练集标准化 | 数据集无显式训练负包且无会话泄漏 |
| P1 | PU-MIL-AE 损失、池化与检查点 | 实现与方法说明一致并通过单元测试 |
| P2 | 审计集评估、消融和自动报告 | 可生成可信的最终指标和会话间波动 |
| P2 | 多厂商适配器和异常恢复 | 新增 App 时不修改通用编排与数据处理代码 |

## 20 分阶段实施计划

### 阶段一 环境可行性验证

1. 准备一台非 Root Android 手机。
2. 开启 USB 调试并确认 ADB 在线。
3. 安装 Appium 和 UiAutomator2 驱动。
4. 启动厂商 App，读取页面结构。
5. 自动完成一次事件操作。
6. 验证手机使用指定公共 Wi-Fi 或蜂窝网络，且与实验网隔离。

完成标准：在不使用坐标点击的情况下，稳定执行至少 10 次操作。

### 阶段二 单设备实验闭环

1. 实现一个厂商 App 适配器。
2. 接入连续抓包。
3. 写入事件 JSONL。
4. 导出 HA 被动日志。
5. 完成时间对齐和结果分类。
6. 试采集两类事件各 20 次。

完成标准：可以从任一成功事件追溯到 App 操作记录、HA 日志和 PCAP 时间窗。

### 阶段三 批量采集

1. 创建 5 个独立会话。
2. 每个会话每类事件执行 40 次。
3. 自动生成正包和未标注包清单，并生成独立评估审计集清单。
4. 执行会话后质量检查。

完成标准：每类获得约 200 个高可信事件包，自动化成功率和状态确认率达到验收要求。

### 阶段四 扩展设备与 App

1. 保持通用编排层不变；
2. 为新厂商 App 添加适配器；
3. 为新设备定义状态机和事件前置条件；
4. 分别验证每个 App 版本和设备固件版本。

## 21 最终建议

本项目应优先采用“实体 Android 手机 + 独立公共 Wi-Fi 或蜂窝网络 + USB ADB + Appium/UiAutomator2”的方案。场地受限时，IoT 设备可改接抓包主机提供的实验热点，并按 3.2 节验收。这不需要 Root，能够保留厂商 App 和厂商云的真实控制路径，同时可由实验主机准确记录每次用户操作的时间。

Home Assistant 在整个过程中只承担被动状态验证和日志输出职责。正包标签以自动化程序记录的 App 操作为主要依据，以 App 状态和 HA 被动日志作为成功确认。通过这种设计，可以把当前低效率的手动实验改造成可连续运行、可审计、可复现的批量采集流程。

训练数据必须保持 PU-MIL-AE 设定，只包含已确认正包和未标注包，不加入人工负包。为了对误报和整体识别性能作出可信判断，另设完全独立、仅用于最终评价的审计真值集。
